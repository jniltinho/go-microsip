## What was done about round 9

| # | Severity | Finding | Response |
| --- | --- | --- | --- |
| 1 | major | Round 8's second answer sent REGISTER and INVITE to one address resolved once, and the library builds the CANCEL of a call without that address and resolves the name for it: with a name that has several addresses, a call canceled while it rang could have its CANCEL sent to another server than its INVITE, and ring on | The answer is withdrawn: nothing is sent to an address of the softphone's choosing any more, and every request goes where the library's own lookup says, as it did in every run and call before round 8. The finding that answer was for (round 8's second) is answered at the filter instead: when something arrives at the account's port from an address the registrar's name did not have, the name is asked again, beside the reading and at most once a second, and the addresses it has now are added to the ones accepted; the response that caused it is refused, and one that comes after the name has answered is accepted (over UDP a REGISTER is repeated after half a second, then at growing intervals, within the ten seconds a registration is given; whether the lookup has answered by the first repeat is not guaranteed). Nothing is taken from the packet itself. `TestTheRegistrarsNameIsAskedAgain`: an address the name did not have is refused, the name is asked once, the address is then accepted, and one the name never has is not. **Open, and the library's:** the CANCEL of a call is addressed by a lookup of its own (RFC 3261, 9.1, wants it sent where the INVITE went), so a name whose answer changes between a call and its cancellation can still have the two sent to different addresses. That was so before these rounds; it is not changed here, and it is stated in the README. Closing it needs a change in the SIP library, which is not vendored. |
| 2 | minor | The library sets a dialog's ended state and then the cause, so the cause could be read before it was there | Fixed. An ended dialog's context is waited for (it is canceled with the cause) before the cause is read, within the three seconds of the cleanup. No test. |
| 3 | minor | The README said signaling is read only from "the address and port the account registered at"; the filter accepts every address the name has had, at the account's port | Fixed. The README says what the code does, and that the CANCEL above is open. |

Also found by the runs on the answers to round 8, not by a reviewer, and fixed in commit `fe82f91`: the engine canceled an endpoint's context before it removed the binding at the PBX, and the cancellation closes a UDP account's socket. The removal used to go out because the library, finding the socket gone, opened another on the same address; with no name lookup before it (round 8's withdrawn answer) it found the socket still listed, and failed. The lab's PBX, which allows one contact, then refused the same account's next registration in 16 of 79 scenarios, and the AppImage walkthrough failed 6 subtests. The binding is removed first now. With the withdrawn answer still in place, which is the case that provoked it, the lab passed 79 of 79 and the walkthrough 30 of 30 on that commit.
