## The built window (Linux, purego, Xvfb in the build container)

`make go-self-test` on this batch:

```
self-test: window opened and the page called the backend
self-test: inline script, eval and a new window refused; navigation to another address refused and the page stayed; no listening socket
```

The self-test runs a probe in the page: an inline script and `eval` (must not run), `window.open` (must return nothing), then `location.href` to another address. The page must still be there two seconds later to answer an event, the guard must have refused the navigation, and the process must have no listening TCP socket.

Control: with the guard counting but letting the navigation through, the same command fails ("the page did not call the backend and answer the probe in time"): the page was replaced.

`docs/prints/go/window.png` is the real window on the real engine with an empty profile: the dialpad, "Disabled", "No account configured" (before this batch it showed "Phone engine unavailable").

Frontend: `vp check` passes (35 files formatted, 24 checked); `vp test run` passes 26 tests (17 of the reducer and validation ported from the Rust UI state tests, 9 of the skins); the embedded build has no inline script and no mock.

## A call placed from the window (`make go-window-call`)

The binary built with the window runs inside the lab network on a display of its own (Xvfb with a window manager), with PipeWire's virtual sound cards and a fresh PBX, for a plain account (1001, UDP) and a secure one (1201, TLS and SRTP). Nothing is scripted inside the application: the keys and the mouse are a person's (`xdotool`), and the test reads the file `--ui-trace` writes, which has every event the engine sent to the page and what the page shows whenever it changes (its text and where its buttons are).

| Step, per account | What is checked |
| --- | --- |
| Start | The account registers on its own; the page shows "Registered" and the account |
| Ctrl+L, 6 0 0, Enter | The engine reports the call established and the page shows "Connected", the number, and "Unencrypted (RTP)" or "Encrypted (SRTP)" as the account needs |
| Ten seconds of sound, the web process stopped for five of them | 1001: 996 of 995 pieces, no silence, arrival gap 22 ms. 1201: 996 of 996, no silence, 21 ms. Inside the threshold; a run that finds no web process to stop fails |
| Mute, Unmute (buttons) | The engine's snapshot and the page agree; muted, the voice is in at most 10 pieces of two seconds; unmuted, it is back |
| Hold, Resume (buttons) | The engine's snapshot and the page agree ("On hold", then "Connected") |
| Menu, Settings, "Windows XP", during the call | The page draws the other skin at once; the engine's call is untouched and three seconds of its sound are whole (1001: 296 of 295 pieces; 1201: 296 of 296); the call is still shown when the settings close |
| Escape | The call ends as normal; the page leaves the call |
| Calls tab | The call is listed: "Out", "Answered", 600 |
| Menu, Settings | The page names what this build cannot do ("Not available in this build": volume, the audio test, CSV import, agent grants) instead of offering it |
| Contacts, Add: a name that is markup (`<img src=x onerror=alert(1)><b>Ana</b>`), typed by a person, for the other extension | The list shows the name as the text it is |
| The other extension calls (a second softphone, `go-microsip run --call`) | The engine reports an incoming call from that number; the page shows "Incoming call" with the contact's name as text and the number; the page holds no image |
| Enter | The call is answered; the strip and the call's panel show "Connected", "From", the name as text, and the protection |
| Xfer, 602, Enter | The engine reports the transfer pending, then succeeded, and the call ended as transferred; the page leaves the call |
| The other extension calls again; Escape | The call ends as rejected, and the caller's softphone reports a call that was not answered |
| Calls tab | Three calls: out and answered, in and answered, in and rejected, with the name as text; still no image |
| Order | No phase appears on the page before the engine sent it |
| SIGTERM | The process exits within 15 s; before that the engine reported the account unregistered and itself stopped |
| The window is started again on the same profile | It draws the skin chosen before (Windows XP), once the settings are read from the database |
| A second window with a password the PBX refuses | The engine reports the registration failed as unauthorized; the page shows "Failed: wrong credentials" and never "Registered" |

Sound in the run on record, ten seconds with the web process stopped for five: 1001, 996 of 996 pieces, no silence, arrival gap 23 ms; 1201, 995 of 996, longest silence 10 ms, 36 ms. Every step after the skin change runs in the Windows XP skin. Log: [`go-m2/window-call.log`](go-m2/window-call.log).

What the runs before the passing one turned up:

- The process ended before the last events were through; the window now waits for them.
- Opening the contact editor or the transfer field did not put the keyboard focus in it (the `autofocus` attribute does nothing for a view drawn later). Fixed with task 4.3, below.
- One run failed at the start because the container's sound service did not answer in time; the next run passed unchanged.

The echo answers at once, so "Calling" and "Ringing" of the outgoing call were sent by the engine but too briefly to be seen on the page. A failed transfer, a call without a sound device and a stopped engine are drawn by the page (the mock's screenshots) but were not produced on the real window.

A display name from the network never reaches the page: the engine names an incoming call by the user part of its address alone. The names a page can show come from the contacts, which is why the hostile name is a contact's.

`make go-call` (the call without a window, whose test shares the sound fixtures) passes after the change: 996 of 996 pieces in both modes.

## Skins

`internal/archtest/skins_test.go` (design D7) fails when other skins than the six have a stylesheet, when a skin lacks or adds a token (it names both; checked by removing one from `win98.css`), or when the page's registry or the values the configuration accepts for `ui.theme` name other skins. The page's own tests keep the finer rules (contrast, no literal color outside the skins).

### System follows the desktop (`make go-vm`, GNOME on Wayland)

The desktop VM check gained a step: the AppImage starts on the System skin with a profile of its own, the desktop is switched to dark and back (`gsettings set org.gnome.desktop.interface color-scheme`), and what the page draws is read from the window's record.

| Guest | Artifacts of `64899df` | Artifacts of `0a67f98` |
| --- | --- | --- |
| Ubuntu 26.04, GNOME 50 | **fail**: the page stayed light | **pass**: dark in 384 ms, light again in 393 ms |
| Debian 13, GNOME 48 | **fail**: the page stayed light | **pass**: dark in 132 ms, light again in 258 ms |

The limit is two seconds; the record is written every 250 ms. The failure was real: WebKitGTK in a plain GTK window keeps `prefers-color-scheme` at light whatever the desktop says. The window now passes the desktop's preference on to the page (a `desktop` event when it subscribes and at every change, from the toolkit's reading of the settings portal), and the System skin is dark when that or the webview's own media query says so. Logs of the passing run: [`go-m2/vm-ubuntu2604.log`](go-m2/vm-ubuntu2604.log), [`go-m2/vm-debian13.log`](go-m2/vm-debian13.log); both guests pass every other step too (headless modes, 20 s of sound, the window), and both VMs were destroyed.

Not verified: the same on KDE, on Windows and on a desktop without the settings portal (there the page keeps the webview's own answer).

## The built AppImage driven (task 4.7)

**With `agent-desktop` on the owner's desktop** (Kubuntu 26.04, KDE on Wayland; the owner allowed the window to open there). The AppImage of `0a67f98` ran on a profile of its own (data, configuration and cache in a temporary directory), against the lab PBX in its host profile (ports on 127.0.0.1 only, new fictional accounts), with sound devices named that do not exist, so the owner's microphone and speakers were never opened.

| Step | Result |
| --- | --- |
| Open | The window opened; the engine registered 1001 with the lab PBX over TCP (the window's own record) |
| `agent-desktop list-apps`, `list-surfaces` | The application and its window "go-microsip" are listed |
| `agent-desktop snapshot` | **Only the window's frame**: six nodes, marked incomplete, with and without the X11 backend. The page is not on the accessibility bus: WebKit's web process does not appear there |
| Dial, hang up | **Not possible with this tool here**: there is no element of the page to act on, and on a KDE Wayland session the tool refuses to send keys or pointer input |
| Close | A termination signal; the engine reported the account unregistered and itself stopped |

Afterwards the PBX was stopped, its fixtures and the temporary profile removed; the desktop entry in the owner's profile was not touched (the application wrote its own into the temporary profile). One variant was not tried: starting the page's process without WebKit's sandbox, to see whether that is what keeps it off the bus, was refused as a safety bypass and left at that.

Two things follow. The task as written cannot be done with `agent-desktop` on this desktop. And the page may be invisible to assistive technology on Linux: a screen reader gets the same six nodes. Whether that is the application, the toolkit or this desktop is not established; it is open.

**With the keyboard and the mouse in the lab** (`make go-appimage-call`). The same AppImage file runs the whole call scenario of `make go-window-call` above, inside the lab network on a display of its own: open, register, dial the echo, the page frozen, mute, hold, the skin changed, hang up, the history, an incoming call with the hostile name, answer, transfer, a refused call, the termination signal, the restart on the saved skin, and the wrong password. Both accounts pass; sound with the page frozen for five of ten seconds: 1001, 996 of 996 pieces; 1201, 996 of 995. Sixteen screenshots, eight per account, are in [`docs/prints/go/appimage/`](../prints/go/appimage/) (a display in a container: fictional data only). What these do and do not show. 150 % on the mock is the browser's viewport enlarged and the page zoomed by the same factor, which gives the page the layout a scaled desktop gives it; it is not a desktop at 150 %. An X11 display scales by whole numbers, so the real window was not run at 150 %; a desktop's larger text setting (`GDK_DPI_SCALE=1.5`) does not reach the page at all, which stays at 100 %. "Legible" is judged by the absence of overflow and clipping and by looking at the screenshots, not measured.

Found and fixed on the way: the contact editor, the transfer field and the settings did not take the keyboard focus when they opened, so a person at the keyboard had to reach the first field with Tab. They take it now, and the lab scenario types the contact's name and the transfer target without clicking.
