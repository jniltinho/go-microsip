## Sound: a first look (2.3, not done)

A macOS-only test (`coreaudio_probe_darwin_test.go`) calls CoreAudio and AudioToolbox from Go through `purego`, with no cgo.

- The device list works: on this Mac, "1 devices: 0 with an input, 1 with an output", which is what the system reports.
- An 8 kHz mono output queue is created, but `AudioQueueStart` fails with -66681 ("cannot start"). The system's own player fails the same way in the same session: `afplay` prints `AudioQueueStart failed (-66681)`. So over SSH, with nobody logged in, macOS starts no audio queue for anyone; this says nothing about the Go path. The test skips on that status.
- The question the probe exists for, whether a callback made on AudioToolbox's thread enters Go on time while the collector runs, is still open. It needs a logged-in desktop session; capture also needs an input device.

## The command line against a running window (4.6): not possible in this session

`go-microsip doctor` on the Mac now names the control folder under Application Support. The window itself could not be kept running over SSH: started normally (not as a self-test) with nobody logged in at the console, the program ends at once with status 0 and prints nothing, having made its control folder and socket. `status`, `call dial` and the MCP server's `status_get` then answer `engine_unavailable` ("go-microsip is not running; nothing was started"), exit 4 for `status`, which is the right answer to a window that is gone. The self-test of the same program opens its window and passes in the same session.

Why the normal start ends was not established. It was looked at as far as this: no other instance holds the toolkit's single-instance lock, and removing that lock file changes nothing. What differs from the self-test is the single instance and the menu-bar item. It has to be looked at again in a desktop session: if the window ends there too, it is a defect of the macOS build, not of the session.

Everything these runs left on the Mac, in temporary folders, was removed.

## A mistake of this run, and how it was undone

The macOS control test was first written with a made-up home path that is not one of the placeholders the publication scan accepts. The path was fictional and named nobody; the scan's rule is about its form. The scan was run before the push and reported it, and the push was made all the same, because the commands were chained without stopping on the scan's failure. The file was corrected in a later commit, but its first version stayed in history, which the scan reads whole, so CI failed on `main` in its two scan steps.

The owner chose to have the history rewritten. The three commits that held or followed that version were replaced by two that never held the path, this one's code commit being `39a18f0`, and `main` was forced to them; the old commits are in no branch.

What that means for the evidence above: the tests on the Mac were run on the code of the first of the replaced commits. The code of `39a18f0` differs from it in that path alone, in two lines of one test, and that test was run again on the Mac after the change and passes.
