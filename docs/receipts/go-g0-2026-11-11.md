## SIP and media (criteria 1 to 5)

`sh docker/asterisk/go-g0.sh` builds `internal/g0/cmd/g0lab` with `CGO_ENABLED=0`, generates new
fictional accounts and a three-day lab CA, and runs it against a fresh Asterisk 22.11.0 on an
internal Docker network. Last run: **35 scenarios, 0 failed**
([report](go-g0/sip-lab-report-2026-11-11.json)). Libraries: `emiago/sipgo` v1.7.0 and
`emiago/diago` v0.42.0.

What the library did not do, and how the spike closes it (design D3, "G0 finding"):

| Gap in diago v0.42.0 | Closed by |
| --- | --- |
| No SRTP/SRTCP replay protection | Patch in `third_party/diago` (receive contexts get a replay window) |
| RTP and RTCP accepted from any address | Same patch: packets from another address are dropped and counted |
| A packet that fails authentication ends the stream | Same patch: dropped and counted, the stream goes on |
| A plaintext offer to a secure account is accepted | The endpoint inspects the audio section and answers 488 |
| A plaintext answer to a secure offer is accepted | The endpoint ends the call before sending or playing audio |
| Requests accepted from any address | Server middleware: registrar address and port only |
| `Serve` opens a listener per transport | TLS and TCP accounts do not serve; calls arrive on the registration's connection |
| `sendonly` keeps sending audio | The engine stops the microphone while a call is held |

The replay, tamper and foreign-source proofs run on a loopback relay that stands between two media
sessions and read through the real RTP session and packet reader; the lab cannot spoof the PBX's
address from another container. `TestWithoutGuardReplayIsAccepted` is the control: with the guard
off, the replay is delivered.

Not proven here, and owed by the engine (M1): renegotiation that tries to drop SRTP, early media
before the answer check, and the same refusals on re-INVITE. Codex marked diago's internal
behavior in these cases as unverified.

## Audio (criteria 6 to 8)

Adapter: `internal/platform/audio`, one backend per OS behind the same engine-side code and
lock-free rings; no cgo on either. The test (`TestPulseLoopback`, `TestWASAPI`) plays a tone and
captures one through the adapter for five minutes at a 20 ms tick and judges it with a meter that
counts against wall-clock time and reads gaps from the audio in 10 ms pieces (`TestMeter` proves
that 60 ms passes and 80 ms fails, batched or not). Every device run includes a control: a 300 ms
stall of the loop must be reported in both directions.

| Where | Capture | Speaker | Verdict |
| --- | --- | --- | --- |
| Build container, PipeWire 1.4.2, virtual cards | 15000 of 15000 frames, no drop | 29992 of 29994 pieces, longest silence 10 ms, arrival gap 43 ms, 22 silent samples | **Pass** |
| Debian 13 VM, its own PipeWire 1.4.2 | 15000 of 15000 frames, no drop | 29976 of 29996 pieces, longest silence 10 ms, 22 silent samples | **Pass** |
| Ubuntu 26.04 VM, its own PipeWire 1.6.2 | 15000 of 15000 frames, no drop | 29896 of 29996 pieces (0.33 % missing), longest silence 10 ms, 54 silent samples, **one 118 ms interval without samples at the listener** | within 0.5 %, **fails the gap rule once** |
| Windows 11 VM, WASAPI, emulated HD Audio without a host backend | 14649 of 15000 frames (2.3 % missing), no gap | 29220 of 29995 pieces (2.6 % missing), no silence, 53760 samples dropped | **fails 0.5 %** |

Reading the two failures:

- **Ubuntu VM**: the adapter fed the device continuously (54 silent samples in five minutes) and the
  audio that arrived had no silence longer than 10 ms; the test's listener received nothing for
  118 ms once. Whether the speaker really paused or only the listener's delivery did cannot be told
  from this fixture. A 20 s run on the same VM passed. It is recorded as a failure of the gap rule in
  that VM, not explained away.
- **Windows VM**: capture delivered 7813 samples per second and playback consumed 7821, against a
  nominal 8000: the emulated card's clock is about 2.3 % slow in both directions, which no real
  sound card is. The adapter kept the call's audio flowing (no gap, bounded delay) by dropping the
  excess. The 0.5 % rule cannot be judged on this VM. It needs a Windows machine with a real sound
  card, or the VM's audio connected to the host's (which plays the test tone on the owner's
  speakers and was not done without asking).

The cgo candidate (`malgo`) was not tried: nothing so far shows the pure-Go backends at fault.

Device loss: on Linux the unplugged microphone is reported, capture stops, the stream is not
moved to another microphone and the speaker keeps playing. On Windows, `Disable-PnpDevice` refused
the VM's virtual card ("Generic failure"), so the loss could not be provoked.

## Window, command line and MCP (criterion 9)

- The Linux window uses the experimental CGO-free backend of Wails 3.1.0 (`-tags purego`); the whole
  Linux binary is built with `CGO_ENABLED=0`. `GO_WINDOW=cgo` builds the cgo backend, which passed
  the same checks and is the fallback.
- `build/qa/headless.sh`: with no display variables, `version`, `doctor --json` and an MCP
  `initialize` + `tools/list` handshake over stdio succeed (both backends).
- `build/qa/self-test.sh`: under Xvfb the window opens and the embedded page calls Go.
- On the owner's desktop (KDE on Wayland) the self-test passed and the window announces the
  application id `io.github.jniltinho.go-microsip`, which is how the title-bar icon is found
  ([print](../prints/go/window-kde.png)).
- Debian 13 VM (GNOME 48 on X11) and Ubuntu 26.04 VM (GNOME 50 on Wayland): the AppImage passed the
  self-test with its default start; `libgtk-4-1` and `libwebkitgtk-6.0-4` came with the
  distribution's desktop and nothing was installed for the application.
- Windows 11 VM: the `.exe` passed the self-test on the WebView2 runtime that ships with Windows.

A first attempt used GNOME Shell's headless mode; no window opened there with either backend, so it
was replaced by the distribution's real session. That mode is not a supported target.
