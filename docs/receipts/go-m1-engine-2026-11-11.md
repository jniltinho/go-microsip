## What the engine scenarios prove

Each scenario drives `internal/core/engine` only through Commands and Events, as a front end will, with `internal/core/ports/memory` standing in for the microphone (a tone) and the speaker (a tone meter).

- Outgoing call to the echo extension over UDP, TCP, TLS with plain RTP and TLS with SDES-SRTP, each with PCMA and PCMU: the tone comes back; the snapshot's `Secure` matches the account.
- Call between two engines (plain and SRTP): incoming call announced with the caller's number, a different tone measured in each direction, remote hang-up ends both sides as normal.
- Hold and resume: while held, the tone of the other side is in under 2 % of the frames each side plays; audio returns in both directions. Mute: the other side receives frames without the tone, the muted side still hears. What the holder puts on the wire is not measured: the send loop sends nothing while held by construction.
- DTMF (RFC 4733) through `SendDTMF`: the PBX reads `123`; a wrong-digits control gets the other tone.
- Blind transfer: the transferring side ends as `transferred` with `TransferSucceeded`; the other party hears the new destination.
- Refusals: Reject (486), do-not-disturb, a second call while busy, cancel while ringing, a plain offer to a secure-media account (488, the sound devices are never opened), wrong password (`unauthorized`, no retry), unknown CA (`certificate`), Dial while not registered.
- Shutdown while established, while dialing and while ringing: exactly one final snapshot, then `Stopped` as the last event; when the event stream closes right after it no sound stream is open, and the whole takes under 5.5 s (measured: tens of milliseconds); the other side sees the call end. If the sound service itself did not answer within the engine's five seconds, `Stopped` would be reported with a device still closing; no test simulates that.

Unit tests add: the outbox keeps final snapshots and `Stopped` for a reader that is away and merges the rest; the command queue is bounded and `Send` refuses beyond it; an unreachable registrar is retried with the bounded delay; a refused renewal is reported and the account registers again once the registrar accepts it (`TestRegistrationRecovers`, a loopback registrar).

## Defects found by these runs and fixed

1. **Reception stayed silent after a hold** (first full run: `engine/hold-mute/*` failed, 25 of 28). The vendored diago jitter buffer keeps counting losses during a silence, so a stream that resumes is late forever. Patched in `third_party/diago/media/rtp_jitter_buffer.go` (marked `go-microsip:`, listed in its README) and pinned by `TestJitterBufferResumesAfterSilence`.
2. **A hang-up sometimes sent no BYE** (intermittent, `engine/pair/1201-1202`: 2 failures in 4 runs). `180 Ringing` was sent beside `Answer`; when it was written after the `200`, the library kept the 180 as the dialog's response and refused the BYE. The actor now sends the final response only after the 180 is out. A hang-up that is not confirmed is logged.
3. **Data race between a renewal and unregistering** (race detector, `TestRegistrationRecovers`). The endpoint now stops the renewal loop before it registers or unregisters. A re-registration on a live endpoint also restarts the renewal, which it did not.

## Real sound through the binary (task 3.8)

`make go-call` runs the built binary (`go-microsip run --call 600 --json`) inside the lab network with PipeWire's PulseAudio server and virtual sound cards: a voice goes into a virtual microphone chosen by ID, the lab's echo sends it back, a listener measures it on a virtual speaker chosen by ID. Neither device is the default one. Plain RTP (1001, UDP) and SDES-SRTP (1201, TLS).

| Run | Account | Speaker, 10 ms pieces heard | Longest silence | Sent / received 20 ms frames |
| --- | --- | --- | --- | --- |
| `make go-call SECONDS=300` | 1001 plain | 29994 of 29995 (0.003 % missing) | 10 ms | 15316 / 15314 |
| `make go-call SECONDS=300` | 1201 SRTP | 29994 of 29995 (0.003 % missing) | 10 ms | 15316 / 15314 |

Both are inside the threshold of design D4 (at most 0.5 % late or lost, no gap over 60 ms), end to end: capture, G.711, RTP or SRTP, the PBX, the jitter buffer, playback. Log: [`go-m1/call-300s.log`](go-m1/call-300s.log).

(Earlier runs, before and between the review fixes, measured 29992 and 29994 of 29996, then 29994 of 29995 and 29995 of 29996.)

Then the microphone is unplugged with another microphone in reach: the binary reports `microphone_lost` exactly once, the voice is gone from the speaker, the other microphone is never heard (0 % of the blocks), the call stays up, and an interrupt ends it with status 130 after `call ... ended` and `stopped`. The lab scenario `engine/microphone-lost` shows the same at engine level.

Found by this run and fixed: the first measurement lost 17.7 % with 240 ms holes about every 1.3 s. The vendored diago jitter buffer scheduled each packet one packet time after the previous release, so timer latency accumulated until the window overflowed. It now follows a timetable and catches up when more packets wait than the delay asks for (`third_party/diago/README.go-microsip.md`); `TestJitterBufferKeepsUpWithAFastSource` loses 42 of 300 packets on the old code and none on the new.

Also with this task: `doctor` reports whether sound is available and why not; `internal/platform/audio.Devices` connects when first used and maps a missing service to the core's "no audio service"; `make go-audio` (the adapter alone, 10 s) still passes.

## Import from the Rust application (task 3.10)

`internal/core/rustimport` implements design D9; `go-microsip import rust-microsip [--apply] [--credential]` runs it. 12 tests, 25 cases (`go test ./internal/core/rustimport`):

- A profile whose account and TLS settings exist only in the TOML file, and a profile whose database has its content only in the write-ahead log: settings and data appear; the Rust directory is byte-identical afterwards, with no new sidecar file. The database written by `rust-microsip 0.1.0-rc.3` itself imports too.
- The import refuses while the Rust application's lock or go-microsip's own is held, and holds both while it copies.
- The committed database is one file (no `-wal`, no `-shm`), at schema 5, with the new keyring reference when the password was asked for; the password is in no file; the Rust keyring is only read.
- A process kill at each of 12 points (after every step, between every rename, and between the keyring write and the database recording its reference) followed by recovery leaves the previous database and configuration file in use together, no staged password, no leftover file, and the import can be run again. A kill after the commit was recorded keeps the import. The kill is simulated by returning at that point without closing the store or cleaning up; a power loss is not simulated (the directories are synced before the journal moves on, which no test proves).
- Recovery takes go-microsip's instance lock and refuses under another holder; a recovery that is itself killed is finished by the next; while the keyring cannot be reached the staged password's reference stays on record and is removed later.
- A start imports nothing: recovery without a journal touches neither side.

Limits, stated plainly: the keyrings in these tests are the in-memory adapters, the real ones arrive in M4, so in the shipped binary `--credential` refuses for now; the lock is flock on the path the Rust application uses (`internal/platform/lock`, tested on its own) and was not cross-checked against a running Rust binary; Windows is not supported yet. `run` and `config import --apply` take go-microsip's instance lock, which is the file `instance.lock` beside the database, so there is one go-microsip per database whatever session starts it: a second one refuses to start, and neither import runs beside a softphone.
